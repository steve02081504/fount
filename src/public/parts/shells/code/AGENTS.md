# code Shell (AI coding sessions)

Web layout: topbar home button (opens the two-pane workspace / conversation picker) + scrollable tab strip + a right-aligned **context chip** (current workspace / char; opens the pickers) / centered message flow / single-card composer. Mode / AI source / shell pills and the power icon button live **inside the composer card**; machine / workspace / char pills (`#composer-targets`) and the hint sit **below the card but collapse once the conversation has entries** (`.code-main.empty-mode` is the only state that shows them — see `docs/ui-details.md`). Selections and lifetime state live in `localStorage` prefs (`code.shell.<user>.*`); the opened tab list (draft + session tabs) and each tab's unsent composer draft live in **backend shell data** (`code.tabs`, `GET/PUT /tabs`) and sync across pages via `BroadcastChannel` (`fount-code-tabs`); sessions live on the target workspace (`.fount/code/sessions/<id>.json`; the backend is authority during generation — it writes a `is_generating` placeholder at run start and replaces it with the final entries on finish, so a page reset mid-run recovers from disk; the frontend still writes edits / `!` shell results outside generation).

`public/llms.txt` carries only the shell intro and API: any UI / layout / shortcut / button-interaction detail belongs in **this file** or [docs/ui-details.md](docs/ui-details.md), never in `llms.txt`.

## Frontend conventions & traps

- **Composer is `createMarkdownRichInput`** (textarea-compatible API). A `contenteditable` element has no `.value` / `.selectionStart` — always read/write via the returned `richInput` (`richInput.value`, `richInput.selectionStart`, `richInput.setRangeText`). Reading `elements.composerInput.value` silently yields `undefined`. Placeholder is mode-dependent: `updateComposerPlaceholder()` swaps the `.fount-markdown-rich-input-placeholder` span text **and must also sync the element's `placeholder` attribute** (markdownRichInput rebuilds the span from that attribute on every focus/click). Note `setRawText`/`setRangeText` do **not** dispatch `input`; programmatic writes never need a `suppressComposerInput` guard.
- **Message layers**: bubbles render `entry.content_for_show ?? entry.content` (agent `content` vs human `content_for_show`); copy / save-as-HTML / drag-export use the show layer, edit edits `content_for_edit ?? content` and clears the show/edit overlays. **Never** collapse the two layers back into one `content` — sessions persist `content` + `content_for_show`/`content_for_edit`/`charVisibility`, and the agent prompt reads `content` only.
- **Markdown rendering regression**: a real persisted reply can leave an orphan bare fence after a tool result and make the rest of a report look like code. `public/src/replyMarkdown.mjs` narrowly repairs that pattern for char *display only*; do not mutate stored content or treat an unclosed language-tagged fence as an error. `test/frontend/stream_render.spec.mjs` checks a multi-round WS conversation, a persisted/reloaded transcript derived from session `9df34984`, and 119-line code-block geometry at desktop/mobile widths. Keep both stream and final/reload assertions when changing reply rendering; a text-only assertion cannot catch the swallowed heading/list or the viewport-height overflow.
- **Streaming traps**: `boot` calls `warmupMarkdownPipeline()` to preheat the markdown pipeline (a cold registry stalls the first preview window); the streaming bubble uses the **trusted** tier (`allowDangerousHtml: true`) so the reasoning `<details>` is visible during generation (a char reply that is mostly tool calls otherwise renders empty); `updateEmptyMode` must treat "currently generating this session" as non-empty (else the streaming bubble is swallowed); the generating bubble is marked `user-content` or the page-watch locale scan warns.
- **Live tool cards**: `tool-output` `start`/`chunk` updates a temporary card in the generating bubble; `end` must remove that card immediately. A generation can continue streaming after a completed `run-js`, and keeping the card until `done` strands it below later text (and duplicates the eventual tool entry). `test/frontend/stream_render.spec.mjs` checks the card and new preview in the same DOM snapshot.
- **Sub-agent runs** (`public/src/subagents.mjs`): a `sub-agent` tool entry carrying `extension.subAgent` renders as a status button (`subAgentCardElement`), spinning while `running`/`summarizing`; clicking opens Agent Studio at `#conversation/subagent%3A<runId>` in a new tab. Live state comes from the server `subagent-run` event (`onServerEvent`, registered in `boot`) filtered by `chat_name === 'code-<sessionId>'`, backed by `GET /api/parts/shells:agent_studio/subagents?chatId=` on tab switch / generation end.
- **Unified async tasks** (`public/src/asynctasks.mjs`): a tool entry carrying `extension.asyncTask` renders as a **non-interactive** status card (`asyncTaskCardElement`) — kind icon + label + live state (spinner while running). Live state mirrors sub-agent: the server `async-task` event (`onServerEvent`, registered in `boot`) filtered by `owner.chatName === 'code-<sessionId>'`, backed by `GET /api/parts/shells:code/async-tasks?chatId=` on tab switch / generation end (the endpoint lists only running tasks; settled results remain awaitable until the parent generation finishes or they are retrieved, while the completion notification is the persistent record).
- **Shared run-card framework** (`public/src/runCards.mjs`): both modules build their card through `createRunCard` / `paintRunCard` and register a `createRunCardFeed` (per-chat state map + 3 s throttled refresh + `chat_name`/`owner.chatName` event filtering + icon-key repaint). `messages.mjs` calls `updateRunCards()` after (re)rendering; `session.mjs` calls `refreshRunCards({ force: true })` on tab switch / generation end (one call for both feeds).
- **Structured tool cards**: `messages.mjs` renders `extension.asyncInspect` (`renderAsyncInspect` → role-tagged transcript for sub-agent payloads, plain latest-output markdown for JS/shell), `extension.asyncList` / `extension.asyncAwait` (`renderAsyncList` / `renderAsyncAwait` → snapshot task rows + result markdown; a state badge appears only when the payload carries a terminal `state`, so `<list-async/>` / unsettled rows never fake "running"). The unified `<inspect-async id="…"/>` tool (`async-task` plugin) replaced `<check-subagent>`; there is no `subAgentCheck` render path anymore. `code/src/entry_extension.mjs` `pickEntryExtension` is the whitelist of extensions persisted to the session — a new render field **must** be added there or the WS `done` path strips it (`sanitizeEntry`). `loadedContextHashes` is kept for a non-render reason: it lets file-operations `<view-file>` skip re-injecting upward `AGENTS.md` / `.agents/docs` context across user turns.
- **Tool labels**: `TOOL_NAME_I18N` maps dot-namespaced tool names (`sub-agent.*`, `async-task.list|await`, `async-task` notice, `code-execution.*`) to `code.tool.*`; `code-execution.async` needs the task `kind` (`geti18n('code.tool.async.run', { kind })`). Unknown names fall back to the triggering XML tag, then the raw name.
- **Generation run identity + backend persistence**: every WS `send`/`regen`/`trigger` carries a client `runId`; the backend echoes `runId` + `sessionId` on **every** frame after a leading `{ type: 'run-start' }`. The frontend stores it in `store.generatingRunId` and drops frames whose `runId`/`sessionId` don't match the active run (`isCurrentRunFrame`), so events from a superseded run can no longer paint over the current round. The backend registers one active run per `username\0sessionId` (a new request aborts the previous run) and **persists the authoritative session to the workspace** — a `is_generating` placeholder before generation, replaced by final entries on `done`/`aborted`/`error`. `ws.close()` only detaches the socket; generation continues and still lands on disk. On reload / socket loss the frontend `recoverGeneration` polls `GET /sessions/:id` until the placeholder is gone, then re-renders (`hasGeneratingEntry`); `store.recovering` blocks new sends meanwhile.
- **Session flush (frontend edits; backend owns generation)**: `markSessionDirty` → flush on `window.blur` / `visibilitychange` / `beforeunload`, and immediately when marked while not generating; the WS `send` carries the whole session, `done` returns entries + `chat_scoped_char_memory` which replaces local state. `sendMessage` optimistically appends the user entry (with `clientEntryId`) before the round-trip; the backend skips echoing when that id is already in the incoming `session.entries`. While `store.generating`, the frontend skips flushing (the backend is the writer); the backend merge is `baseEntries + allNewEntries + requestSession.entries` deduped by id.
- **Incremental entries (append during generation)**: an agentic reply spans many rounds, so the backend emits `{ type: 'entries-append', entries }` **before** each `preview` — `endpoints.mjs` `flushIncrementalEntries` reads `requestSession.generationResult.logContextBefore` (exposed by `request.mjs` `replyPreviewUpdater`; the char template fills `base_result`), tracks an `emittedLogCount` watermark, and `done`/`aborted`/`error` only send the remainder. The frontend `session.mjs` `insertIncrementalEntries` dedupes by id and inserts each fresh bubble **before the generating bubble**, so completed tool logs / earlier rounds append live instead of the whole reply flushing at `done`.
- **`fount run`**: `run` uses the last-active user and the CLI cwd as the workspace; the page opens with `?workspace=<id>` and `boot()` prefers that query param over the localStorage pref.
- **`fount.user.send`**: boot registers `globalThis.fount.user.send(string | chatLogEntry)` — same syntax as chat (`normalizeUserSendPayload`); `content.content` goes to the current session, `files[]` join the attachment queue.
- **Locale check / page watch**: rendered message bubbles and the session title are dynamic user/AI text — mark them `user-content` (empty value); tool/system bubbles and structured prompt cards (tool logs, sub-agent transcripts) are prompt content — mark them `prompt-content`. Rendered chrome (empty-state, home picker rows, tab strip, pill labels) re-renders via `rerenderDynamicText` / `refreshHomePicker` on language change. Avoid adding **new i18n keys** on feature branches without syncing ja-JP/en-UK; page-watch rotates only zh-CN → ja-JP → en-UK, so **en-UK must be real Latin text**.
- Register the `onLanguageChange` rerender **inside `boot` after `initTranslations('code')`** — module-top-level registration warns before the bundle loads; module-top-level `geti18n()` also warns.
- **Theming**: `index.css` references daisyUI **full-spelled** semantic vars only (`--color-base-100` / `--color-base-content` / `--color-primary` … via `var()` / `color-mix`) — no `:root` hardcoded fallback, no `--b1` abbreviations. Radius via `--radius-box|field`, border width via `--border`. Markdown code-block syntax highlighting (shiki dual-theme `--shiki-*` vars) depends on the `color-scheme` **attribute** set by `preload.mjs` / `theme/index.mjs` (`updateColors`) — the `[color-scheme*="…"]` selectors in `pages/scripts/features/markdown/convertor.mjs` never match the old `documentElement.colorScheme` expando. Write only the attribute; `base.css` derives the CSS `color-scheme` property from it (do not also set `style.colorScheme`).
- **Icons**: no hand-written `<svg>` (enforced by `checks:no_manual_svg`); icons come from the Iconify CDN as `<img class="text-icon">`, inlined by `renderTemplate` / `svgInliner`, or by `applyTheme()` for static page icons.

Deep UI (layout, home picker, tabs, folder browser, shell mode, history/ghost, slash/mention, bubbles, tool cards / async tasks, message actions, attachments, power actions): [docs/ui-details.md](docs/ui-details.md).

## Backend (src/)

- `main.mjs` `ArgumentsHandler(user, args, context)` (also `IPCInvokeHandler`) registers `context.cwd` as a machine-0 workspace (creating it) and opens `/parts/shells:code/?workspace=<id>` via `npm:open` (`config.port` for the URL). `--prompt|-p` and `--workspace|-w` (default CLI cwd) are parsed by `parseRunArgs`; with a prompt the backend first tries to hand off to an **open page** (`requestExternalOpen` broadcasts a `code-open` event with a nonce, waits ≤800 ms for a page to `POST /open-claim`); if none claims, it opens the page with `?prompt=` (boot creates a draft tab and sends immediately). The claiming page creates a draft tab in the target workspace, focuses/flashes via `flashWindowFocus`, and sends the prompt.
- **Workspace hooks** (`src/hooks.mjs` + pure `src/hooks_config.mjs`): `.agents/fount/code.json` `hooks.agentStart|agentFinish|agentsIdle` are shell-command lists run on code top-level runs **and** sub-agent runs (sub-agent events come from the internal `events.on('send-event-to-user')` `subagent-run` stream, filtered to `chat_name` starting with `code-`). Agent counts are per workspace (`machine\0path`); `agentFinish` hooks are awaited **before** the counter decrements so a hook-triggered regen increments first and never trips `agentsIdle`. Event data is passed as `FOUNT_CODE_*` env vars (see `public/llms.txt`). A non-zero `agentFinish` exit feeds merged stdout+stderr back as a system entry and triggers a regen (≤`MAX_REGEN_ATTEMPTS`=3 per session, reset on success); `detached` entries run via `launch_external` (local only) with optional `singleton`. `setHookRuntime({ regen })` injects the endpoints-side regen (`regenCodeSession`) to avoid a module cycle.
- `runner.mjs` `runShellCommand` accepts `env` (local only, merged with `process.env` via `target.execShell`'s `env` option) and `timeoutMs` (default `null` = unlimited, preserving user `!` command semantics); hooks pass an explicit timeout.
- `request.mjs` builds `chatReplyRequest_t` by hand: world = inline `codeWorld` (injects selected profile + workspace AGENTS.md), plugins = `code-execution` + `file-operations` + `async-task` (the char's own plugin set, e.g. `sub-agent`, is merged by its `GetReply`), request-level `ai_source` / `workdir: {machine, path}`, and `extension.generationId` (per-round id that sub-agent runs use as `parentId`). `triggerCodeReply` resolves world `GetCharReply` first, falling back to the char's `GetReply` — **`await` each candidate explicitly**. The parent generation is recorded by the char template's active-recording calls (`request_record.mjs`), keyed by the request's `chat_id` (`code-<sessionId>`) and labeled `source: 'shells/code'` from `extension.agentStudio`; the shell no longer writes records itself.
- **Async code execution** (`async-task`): `<run-js async="true">` / `<run-<shell> async="true">` returns a unified task id immediately; results are delivered as a system notification unless awaited. `<list-async/>` / `<await-async>` manage one or more tasks (`mode="all|any"`). JS is still in-process and uninterruptible, async or not. `GET /async-tasks?chatId=` reads the in-memory registry (`plugins/async-task/registry.mjs`, same module instance the plugin loads) for running tasks of the chat. `entry_extension.mjs` holds the extension whitelist for session persistence.
- **Async completion notification**: `registry.mjs` `deliverNotification` appends the notice as a **char-visible system entry** via the request's `AddChatLogEntry` (code shell: into the live `requestSession.entries`, so a running regen round's `injectRoundEntries` collects it via `Update`; also pushes `code-async-entry` to the frontend). The shell decides triggering, not the char: if the frontend is idle it appends the entry and sends WS `trigger` (generate from the current session, no new user message); if generating it sets a pending flag cleared by `code-async-consumed` (backend `ClearPendingMessages`, emitted on every `injectRoundEntries`) or, if never consumed, fires one follow-up `trigger` on `done`. Sessions stay frontend-owned; the backend only mutates its own `requestSession` copy.
- `runner.mjs` `runShellCommand`: no workdir falls back to the **target machine's** `os.homedir()` via `execJs` (never the server cwd / system32). User `!` commands run **without a timeout** (`timeoutMs: null`) and return `elapsedMs`. AI `<run-*>` timeout policy (default 3 min, `expect`+`tolerance`, `wait="forever"`) and large-output spill live in `src/scripts/shell_guard.mjs`, shared with `plugins/code-execution`. Streaming plumbing (local `@steve02081504/exec`, remote `callback`): [docs/ui-details.md](docs/ui-details.md).
- `lifecycle.mjs`: per-user active-generation counter + pending power actions (`Map<machine, action>`). Every WS `send`/`regen` calls `beginCodeGeneration` and the `finally` calls `finishCodeGeneration`; at 0 with pending actions it runs each host's OS power action (`shutdown` / `sleep` / `restart`) via `createTargetExecutor(...).execShell(null, cmd, { timeoutMs: null })` — remote hosts first, local delayed ~800ms so the `done` response gets out. On successful `done` it fires `notifyCodeCompletion` → `notifyUserI18n` → `notifyUser` (live `/ws/notify` → Web Push → desktop fallback; shared lib `src/server/web_server/notify/`).
- **Exit/resume boundary**: `src/shutdown.mjs` installs synchronous signal listeners alongside `on-shutdown` and records process-level state via `scripts/stopping.mjs`. Ordinary `process.exit` stops launching new AI rounds (templates check `generation_options.finishRound()` at the regen decision; nested sub-agents read injected `deps.isStopping`), awaits the current AI call + reply handlers and session write; `SIGINT`/`SIGTERM`/`SIGHUP` abort active calls (templates call `signal.throwIfAborted()` after `StructCall`), allow up to 3 s for cleanup, and retain the job. For workspace-backed runs, the `StartJob` snapshot (including user input) precedes the generating placeholder; successful persistence of completed/explicitly aborted runs calls `EndJob`. `interfaces.jobs.ReStartJob` starts a detached resume from disk/snapshot after boot, strips the placeholder, appends a system notice with the shutdown reason and elapsed gap, and re-enters the same generation path. Session HTTP writes/deletion return 409 while the job or run exists. `finishRound` also commits the finished round so forced aborts never persist a half-written round.
- **System sleep**: `src/scripts/sleep_watch.mjs` checks 1 s ticks for gaps over 5 min. Sub-agent deadlines and shell/JS/async-await timers exclude detected sleep, and code/sub-agent conversations receive a system notice; test synthetic gaps via `checkForSleep` and always restore a mocked clock afterward.
- `history.mjs`: native shell history files (pwsh/powershell `ConsoleHost_history.txt`, bash `.bash_history`, zsh `.zsh_history`) via a self-contained `execJs` lambda + own history at `.agents/fount/code/{shell,message}_history.json` (dedupe, cap 500).
- `workspace_config.mjs`: reads `.agents/fount/code.json` (char override / install URL).
- `editor_sources.mjs` `collectEditorSources`: editor project dirs from a self-contained `execJs` lambda (VS Code + forks, Notepad++, JetBrains family); deduped by **realpath**, sorted by last active. Editor scan (5 min) + volume labels (1 h) are memoized with TTL (`src/scripts/memo.mjs`); the editor-source cache key includes the **APPDATA/XDG_CONFIG_HOME fingerprint**. `boot()` warms it in the background. Details: [docs/ui-details.md](docs/ui-details.md).
- Targets resolve through `plugins/file-operations/src/target.mjs` (`createTargetExecutor`): machine 0 = local (`node:fs` + exec), machine > 0 = subfount executors. `listMachines(username)` backs `GET /machines` and `<list-machines>`.
- Sessions are validated with `/^[A-Za-z0-9_-]{1,64}$/` before touching the fs; `GET /sessions/all` aggregates summaries across all saved workspaces (with `workspaceId`/`workspaceName`).
- Shell data gotcha (repo-wide): `saveShellData(username, shell, name)` persists the **in-memory cache entry**, not a passed value — mutate the object returned by `loadShellData` first, or call `assignShellData` to swap the value.
